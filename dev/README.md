# Jellybeam dev test environment

A disposable, fully containerized Jellyfin server plus a synthetic media
corpus, for exercising the Jellybeam macOS client against a real Jellyfin
backend without needing real media files or any host installs beyond
Docker itself.

## Quick start

```
dev/server.sh corpus      # generate the synthetic media library into dev/media/
dev/server.sh up   # docker compose up + first-boot wizard automation
```

The compose services bind to loopback only, and mount the synthetic corpus
read-only. The seeded accounts are for this local dev environment.

Then point Jellybeam (or any Jellyfin client) at `http://localhost:8096`:

| User | Password | Role |
|---|---|---|
| `jellybeam-admin` | `jellybeam-test` | Administrator |
| `jellybeam-user` | `jellybeam-test` | Standard (non-admin) |

`dev/server.sh up` prints a fresh admin API access token on every run (also
emitted alone on stdout, for scripting) if you want to hit the REST API
directly instead of logging in through a client.

### Opt-in: a second server for Jellyfin 12.0

A second, disabled-by-default server targets `jellyfin/jellyfin:12.0`
instead of the pinned 10.11.10 line, for testing against a newer server
without disturbing the main dev server's database:

```
dev/server.sh 12-up   # docker compose --profile v12 up + first-boot setup, on :8097
```

It's the `jellyfin12` compose service, gated behind the `v12` compose
profile, so plain `docker compose up` / `dev/server.sh up` never start it.
Same users/libraries, on `http://localhost:8097`, with its own named
volumes (`jellyfin12-config` / `jellyfin12-cache`) — entirely separate
from the pinned server's state.

- `dev/server.sh 12-up` — bring it up + run setup.
- `dev/server.sh 12-down` — stop just the `jellyfin12` container (config/cache survive); the pinned `jellyfin` service is untouched.
- `dev/server.sh 12-reset` — drop only the `jellyfin12` volumes and start clean; the pinned server's volumes are untouched.
- `dev/server.sh 12-logs` — tail its logs.

To point the live cargo test suite (`dev/run-server-suite.sh`) at it
instead of the pinned server, set `JELLYBEAM_DEV_SERVER_URL`:

```
JELLYBEAM_DEV_SERVER_URL=http://localhost:8097 dev/run-server-suite.sh
```

`JELLYBEAM_DEV_SERVER_URL` defaults to `http://localhost:8096` (the pinned
server) everywhere it's read. It's independent of `JELLYBEAM_E2E_SERVER`,
which does the same thing for the app's own `JELLYBEAM_E2E=1` verification
mode (`crates/app/src/e2e.rs`) — set whichever one matches what you're
running.

## What's here

| File | Purpose |
|---|---|
| `dev/docker-compose.yml` | The `jellyfin` service: pinned image, port 8096, named volumes for `/config` and `/cache`, `dev/media/` bind-mounted at `/media`. Also the opt-in `jellyfin12` service (see above): `jellyfin/jellyfin:12.0`, port 8097, `v12` profile. |
| `dev/setup-server.sh` | Idempotent first-boot automation over the REST API: drives the startup wizard, creates the two test users, creates the Movies/Shows libraries, triggers a scan. Takes the target server's base URL as its one argument. |
| `dev/media/` | Generated by `dev/corpus/gen-corpus.sh` (git-ignored — see `dev/.gitignore`). Bind-mounted into both servers' containers. |
| `dev/corpus/gen-corpus.sh` | Host-side wrapper: runs `dev/corpus/build-matrix.sh` inside a `linuxserver/ffmpeg` container to populate `dev/media/`. See `dev/corpus/README.md` for the full file matrix and design notes. |

## Jellyfin version

**Client support floor: Jellyfin 10.11.**

The pinned `dev/docker-compose.yml` `jellyfin` service is
`jellyfin/jellyfin:10.11.10` — the oldest supported line, so the default
suite validates the floor. Bump the tag deliberately (with a
`dev/server.sh reset`, since 10.11 replaced the item repository and a
fresh DB beats an in-place migration for a disposable dev server) and
reset the server with it; don't float on `latest`, since that breaks
reproducibility between runs and between machines.

The opt-in `jellyfin12` service (see above) pins `jellyfin/jellyfin:12.0`
for testing against the next major line ahead of time; see the `image:`
comment in `dev/docker-compose.yml` for that tag's own caveats.

## dev/server.sh commands

Run these from the **repo root**, not from `dev/`.

- `dev/server.sh up` — `docker compose up -d` + run `dev/setup-server.sh`. Safe to run repeatedly; the setup script detects what's already done (wizard completed, users/libraries existing) and only fills in the rest, then re-triggers a scan.
- `dev/server.sh down` — stop the container, keep its volumes (config/cache survive).
- `dev/server.sh reset` — `docker compose down -v` (drops config/cache), deletes `dev/media/`, regenerates the corpus, brings the server back up, and re-runs setup from a totally clean slate.
- `dev/server.sh corpus` — generate the synthetic media into `dev/media/` (idempotent; only fills in missing files). Pass `--force` to `dev/corpus/gen-corpus.sh` directly to wipe and regenerate everything.
- `dev/server.sh logs` — tail the Jellyfin container's logs.
- `dev/server.sh doctor` — sanity-checks: Docker daemon up, `jellyfin/jellyfin:10.11.10` and `linuxserver/ffmpeg:latest` images present, `dev/media/` populated, server responding on `:8096`; also reports the opt-in `jellyfin/jellyfin:12.0` image and `:8097` server without failing if that server just isn't started.
- `dev/server.sh 12-up` / `12-down` / `12-reset` / `12-logs` — see "Opt-in: a second server for Jellyfin 12.0" above.

## How `setup-server.sh` drives the startup wizard

Jellyfin's first-run setup is normally a browser wizard. The script instead
calls the same REST endpoints the wizard calls,
in order (all confirmed against the `jellyfin/jellyfin` source at
`Jellyfin.Api/Controllers/StartupController.cs`,
`Jellyfin.Api/Controllers/LibraryStructureController.cs`, and
`Jellyfin.Api/Controllers/UserController.cs`):

1. Poll `GET /System/Info/Public` until the server responds and check
   `StartupWizardCompleted` — this also drives idempotency: if it's
   already `true`, the wizard steps are skipped entirely.
2. `POST /Startup/Configuration` — server name, UI culture, metadata
   locale.
3. `POST /Startup/RemoteAccess` — remote access / UPnP off (local dev box
   only).
4. `GET /Startup/User` — this has a side effect: it calls
   `IUserManager.InitializeAsync()`, which auto-creates the first
   (admin) user if none exists yet. Has to happen before the next step.
5. `POST /Startup/User` — sets that first user's name to `jellybeam-admin`
   and password to `jellybeam-test`.
6. `POST /Startup/Complete` — flips `IsStartupWizardCompleted`.

After that, it's normal authenticated REST calls:

- `POST /Users/AuthenticateByName` to get an admin access token.
- `POST /Users/New` to create `jellybeam-user` (non-admin by default).
- `POST /Library/VirtualFolders?name=...&collectionType=...&paths=...`
  to create the `Movies` (`collectionType=movies`) and `Shows`
  (`collectionType=tvshows`) libraries pointing at `/media/Movies` and
  `/media/Shows` inside the container. Remote metadata/image fetchers are
  explicitly disabled per item type in the request body — see
  `dev/corpus/README.md` for why (short version: without this, Jellyfin tries
  to identify the synthetic codec-named files against TheMovieDB and
  renames them to unrelated real movies).
- `POST /Library/Refresh` to kick off a scan.

All authenticated calls use the standard `Authorization` header with the
`MediaBrowser` scheme (`Client=...`, `Device=...`, `DeviceId=...`,
`Version=...`, and `Token=...` once authenticated) — the same header
format any Jellyfin client uses. (Previously this used the legacy
`X-Emby-Authorization` header name; switched because Jellyfin 12.0
rejects it by default — legacy authorization is disabled unless
re-enabled server-side. The `Authorization` header carries the identical
value and works unchanged against 10.10/10.11.)

## What a successful run looks like

Running `dev/server.sh corpus && dev/server.sh up` against a clean environment and
checking via the API confirms:

- 33 files generated into `dev/media/Movies/`, 4 into
  `dev/media/Shows/` (2 series).
- After the triggered scan completed: `GET /Items?IncludeItemTypes=Movie`
  → `TotalRecordCount: 33`; `IncludeItemTypes=Episode` → `4`;
  `IncludeItemTypes=Series` → `2`. All 33 movie titles are distinct.
- Both `jellybeam-admin` and `jellybeam-user` authenticate successfully via
  `POST /Users/AuthenticateByName`; `jellybeam-user`'s policy confirms
  `IsAdministrator: false`.
- Re-running `dev/setup-server.sh` against an already-set-up server is a
  no-op for the wizard/users/libraries (confirmed via log output) and
  just re-triggers a scan.

## Troubleshooting

- **`dev/server.sh doctor`** first — it'll tell you if Docker isn't running, an
  image is missing, the corpus is empty, or the server isn't up.
- **Container unhealthy / setup script times out waiting for the
  server**: `dev/server.sh logs` to see what Jellyfin is doing. Cold start
  is normally ~5-10 seconds.
- **Setup script can't authenticate after the wizard**: this can happen
  if a previous partial run already set a password on the first user via
  a *different* password than `jellybeam-test` — `POST /Startup/User`
  rejects password changes once a password is already set (by design, to
  prevent hijacking a wizard mid-flight). Use `dev/server.sh reset` to
  start clean rather than trying to patch around it.
- **Ports**: the compose file publishes `8096` directly (no offset). If
  something else on the host is already using `8096`, stop it or edit
  the `ports:` mapping in `dev/docker-compose.yml`. The opt-in `jellyfin12`
  service publishes `8097` the same way. Both bind to `127.0.0.1` only.
